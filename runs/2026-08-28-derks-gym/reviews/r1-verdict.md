- Verified at head: the only parse tolerance is stripping ONE leading/trailing code fence; the remainder must be exactly one JSON object:
  ```python
  def legal_picks(text: str, observation: dict) -> dict | None:
      try:
          payload = json.loads(strip_one_fence(text))
      except (json.JSONDecodeError, ValueError):
          return None
  ```
  A reply of the form `Here is my draft: {"arm":…}` (prose around a valid JSON object) fails `json.loads` and is rejected; nothing anywhere attempts to locate/extract the embedded JSON object. The test suite pins the strict behaviour deliberately (`tests/test_llm_player.py:78` rejects `"sure! here you go"`; no prose-wrapped-JSON acceptance case exists). The design note pins this as "one tolerance, stated, so it is testable" — but the checklist, not the note, defines blocking.

The retry (`derk_player.py:243-265`, one retry at `temperature: 0` with the reminder line), the scripted fallback (`derk_player.py:266-269`), and the recording (`draft_fallback=scripted reason=<…>` to stderr; server-side `fallback`/`fallback_cause` per draft record and `results.draft_fallbacks`) are all present and tested — the tolerance clause alone is falsified. Unlike items 7/10/11, whose literal text is canonical-lineage-flavoured and maps onto this lineage, this clause is pure behaviour and implementable identically here; the builder chose strictness. Each prose-wrapped reply burns the single retry and can end in a scripted fallback, which phase 60 penalises for champions.
- What settles it: extract the first balanced JSON object from the reply text before the legality check (plus a test feeding prose-wrapped JSON), or an explicit checklist-owner ruling that the stated single fence tolerance satisfies item 8.
